## 1. What's healthy

This project has a lot of genuinely careful work in it. Specifically:

- **The concurrency story is written down and consistent.** `FolderPathCache`
  (`organize_service.py:82`) uses per-partial-path locks over a process-wide
  singleton, with a re-check under the lock and a root-id in the cache key so a
  mid-run library reconfig can't cross paths. `scan_service._process_file` holds
  the shared `get_book_write_lock()` around *only* the DB sections, leaving
  download/parse/candidates/AI fully concurrent. Every "why" is in a comment
  (httplib2 not being thread-safe → fresh `DriveProvider` per file; the
  pytest-asyncio per-loop lock rebind → `conftest.py` resets). This is the kind
  of thing most codebases get wrong silently.
- **Computed-confidence-is-authoritative is enforced structurally, not by
  convention.** `ai_reported_confidence` is stored on `ai_decisions` and shown in
  the UI but is never threaded into the routing path; `needs_human_review` is
  always `breakdown.total < 85` (`identification_service.py:93,140`). The
  deterministic fast path deliberately tops out at 95 by never earning the
  `ai_corroborates` point (`confidence_service.py:40-45`).
- **Cost control on the reident deep-check is exemplary.** Free pass reconstructs
  evidence + candidates from stored rows, reuses cached `ai_decisions`, caps the
  AI pass at 50/run, shows a padded `$` estimate first, and there's a test that
  fails if the free pass makes any call (`reident_audit_service.py:8-22,86-88`).
- **sha256 stickiness survives the metadata rewrite.** `original_sha256` is
  matched alongside `sha256` everywhere it matters (`scan_service.py:676-686`,
  `sticky_resolution.py:19-33`), and `embedded_metadata_key` stops re-run hash
  churn.
- **Hostile-input EPUB parsing is real**, not aspirational: defusedxml, per-entry
  and cumulative zip-bomb caps, entry-count cap, wall-clock parse timeout, all
  tested (`test_epub_parser.py`).
- **The series-merge hallucination guard degrades safely** — an unrecognised
  canonical name becomes "review manually", never a silent pick
  (`series_merge_service.py:162-178`).
- **Tests all green, no skips.** `backend` 353 passed (11.8s); `library-viewer`
  60 passed + build + oxlint clean; `frontend` `tsc -b` + build clean + oxlint
  clean. Coverage is broad — every service has a `test_*` file.
- **`ROADMAP.md`'s "Done" section is an unusually honest changelog** — it records
  reverts (`.cbz` convert-then-revert), follow-up caveats, and deferred calls
  with reasons.

## 3. Findings

### P0-1 — Fuzzy title matching collapses distinct same-author books into one, and "Clear duplicates" then trashes the survivors

**Where:** `text_match.py:5,16-32` (`normalize_title` / `_SUBTITLE_SEPARATOR_RE`) →
`book_repository.py:54-68` (`resolve_book`) → `duplicate_service.py:40-52`
(`detect_same_book_duplicates`) → `duplicate_service.py:104-128` (`clear_duplicates`)
→ `frontend/src/pages/Duplicates.tsx:44-86` (bulk "Clear duplicates" button, also
surfaced on `Dashboard.tsx:584-611`).

`normalize_title` strips everything from the first `:` or `;` onward. So every
book whose EPUB `<dc:title>` is `"<Series>: <Title>"` — an extremely common
format for store-bought and release-group epubs (Kobo, Google Play, Tor) —
normalizes to just the series word:

```
'Mistborn: The Final Empire'      -> 'mistborn'
'Mistborn: The Well of Ascension' -> 'mistborn'
'Star Wars: Heir to the Empire'   -> 'starwars'
'Star Wars: Dark Force Rising'    -> 'starwars'
```

`resolve_book` matches an incoming title against every existing book **by the
same author** using `normalize_title` equality (`book_repository.py:60-68`), so
the second book resolves to the first book's row. Confirmed end-to-end against an
in-memory DB with the real services:

```
book1 id 1  canonical 'Mistborn: The Final Empire'
book2 id 1  canonical 'Mistborn: The Final Empire'   <-- SAME ROW
detect_same_book_duplicates flagged: 1
  d1 a.epub  organised
  d2 b.epub  duplicate / same_book
```

**What breaks, and when:**

1. On the next scan or `run_rebuild`, `detect_same_book_duplicates` groups the
   two files by `book_id`, keeps the best-quality one and flags the rest
   `status=duplicate` / `same_book`. This is automatic — no user action.
2. `status=duplicate` files are excluded from organize and from the library
   index, so **the family viewer silently loses N-1 of every affected series**,
   and the one remaining book shows the wrong title for the others.
3. `detect_same_book_duplicates` also re-flags already-`organised` files
   (`_ACTIVE_STATUSES` includes `organised`, `duplicate_service.py:19`), so a
   book that's been in the library for months can flip to `duplicate` because a
   new colliding book arrived.
4. If James then clicks "Clear duplicates" (a single bulk button, presented as a
   routine checklist step on the Dashboard), `clear_duplicates` calls
   `trash_file` on the Drive file and hard-deletes the `File` row plus its
   `Review`/`Operation`/`AIDecision`/`BookCandidate`/`MetadataSource` rows. The
   Drive file is recoverable from Trash for ~30 days; the DB rows are not.

`review_service.correct` (`review_service.py:148`) and
`sticky_resolution.resolve_corrected_book_id` reach the same `resolve_book` path,
so a manual correction can trigger the merge too (already noted in the
`project_bookbrain_ai_series_hallucination` memory for the `/correct` case — this
review adds the `detect_same_book_duplicates` + `clear_duplicates` escalation).

**Fix:** make the row-identity match in `resolve_book` stricter than the
scoring-time match. Match existing books on a normalization that keeps the full
title (articles/punctuation folded, but **no** subtitle/`:` stripping and no
trailing-paren stripping) so `"Mistborn: The Final Empire"` and
`"Mistborn: The Well of Ascension"` stay distinct rows; keep the loose
`normalize_title` only inside `confidence_service` where a false match merely adds
points. Independently, `detect_same_book_duplicates` should require more than
`book_id` equality before flagging `same_book` (e.g. also compare a strict title
key and/or size), and `clear_duplicates` should skip / separately confirm
`same_book` rows rather than sweeping them into the exact-content bulk clear.
Prompt: `prompts/06-title-collision-false-duplicates.md`.

### P1-1 — `applyChanges` in the viewer can drop a file whose change payload omits `parents`

**Where:** `library-viewer/src/lib/librarySync.ts:112-121`.

For every live non-folder change the code computes
`parentKnown = (file.parents ?? []).some(p => folderIds.has(p))` and, if that's
false, **deletes the file from the cache** (`filesById.delete(file.id)`). The
Drive `changes.list` call requests `parents` (`drive.ts:116-118`), but Drive does
not guarantee `parents` is present on every change record (it's absent for items
with no parent in the user's own My Drive, and has been observed missing on
some change deltas). When that happens for a file that's genuinely still in the
library, the incremental sync silently removes it and then advances the page
token past the change, so it stays invisible until the 24h `AUTO_REBUILD_INTERVAL`
fires.

This is the same shape as the "brand-new nested folder" bug the file's own
comment describes. The 24h rebuild is a real backstop, so this is P1 not P0, but
the window is a full day and the user gets no signal.

**Fix:** when a change record has `file` present, not removed, not trashed, and
`parents` is `undefined` (as opposed to `[]`), treat it as "no information about
placement" and **leave the existing cache entry untouched** rather than deleting
it. Only delete on an explicit `removed`/`trashed`, or when `parents` is present
and contains no known folder. Prompt:
`prompts/07-librarysync-missing-parents.md`.

### P2-1 — Model/migration drift: `files.status` and `files.status_reason` enums; `alembic check` is red

**Where:** `data/models.py:26-43` vs
`alembic/versions/a4b6cf91c1a2_init_schema.py:69-70`.

`alembic check` against a fresh `alembic upgrade head` DB fails:

```
Detected type change from VARCHAR(length=14) to
Enum('multi_parent','no_parent','manual_drift','parse_failed','low_confidence',
     'previously_rejected','same_book', name='filestatusreason') on 'files.status_reason'
FAILED: New upgrade operations detected
```

The model's `FileStatus` has gained `rejected` and `FileStatusReason` has gained
`previously_rejected` and `same_book` since the init migration, with no migration
recording it. On SQLite this is harmless today — SQLAlchemy's `Enum` emits no
`CHECK` constraint by default, so the column is a bare `VARCHAR` and the new
values write fine (hence 353 green tests). But:

- there is no automated schema-drift gate — `alembic check` isn't run anywhere,
  and if it were (CI, pre-commit) it would fail;
- the SQLite column length is `VARCHAR(14)`; `previously_rejected` is 19
  characters. Any move to a length-enforcing DB (SPEC §9 names Postgres as the
  path) via a hand-written or naïvely-autogenerated migration truncates it.

**Fix:** add a migration that brings the two enum types in line with the models
(a `batch_alter_table` recreate on SQLite; a real `ALTER TYPE ... ADD VALUE`
sequence for the eventual Postgres migration), and wire `cd backend && alembic
check` into the test run so this can't silently reappear. Prompt:
`prompts/08-alembic-enum-drift.md`.

### P2-2 — `OrganizeService._write_lock` is not reset between tests; three write locks don't serialise against each other

**Where:** `organize_service.py:184` (the lock), `tests/conftest.py:15-27`
(the reset fixture that omits it).

`_reset_shared_singletons` resets `book_repository._book_write_lock`, the folder
path cache, `series_merge_service._write_lock`, `nightly._nightly_lock` and
`metadata_writeback_service._write_lock` — its docstring presents this as the
complete list. It misses `OrganizeService._write_lock`, an instance attribute on
the module-level singleton `_organize_service`. Today only one test
(`test_run_scan_auto_organizes_eligible_files_after_scanning`) acquires it via the
singleton, so no cross-test event-loop rebind surfaces. The moment a second test
exercises scan→auto-organize (or the organize singleton directly), it will fail
with `RuntimeError: <Lock> is bound to a different event loop` — exactly the
failure the other five resets exist to prevent.

Secondary point: there are now three independent commit-serialisation locks
(`_book_write_lock`, `OrganizeService._write_lock`,
`series_merge_service._write_lock`). Each only serialises its own service, so the
"slow Windows fsync exhausts `busy_timeout`" scenario the locks exist to prevent
is still reachable when, e.g., a manually-triggered organize overlaps a nightly
scan's tail, or a series merge overlaps either.

**Fix:** the minimal fix is `reset_organize_write_lock()` + a call in
`conftest.py`. The better fix is to have organize and series-merge commit under
the shared `get_book_write_lock()` (as `review_service` already does), collapsing
three locks to one and closing the cross-service gap. Prompt:
`prompts/09-organize-write-lock.md`.

### P2-3 — Series-merge moves are logged as undoable but "Undo" leaves a broken state

**Where:** `series_merge_service.py:257-323` (writes `Operation(move_and_rename,
dry_run=False, status=done)` per file and can `session.delete(series)`),
`operation_service.py:54-88` (`undo_operation` treats any completed non-dry-run
`move_and_rename` as undoable), `frontend/src/pages/Activity.tsx` (per-row Undo
button).

Prompt 01 required merge moves to be "undoable (SPEC §9)". They produce Operation
rows, but `undo_operation` for one of them:

- moves the Drive file back to `operation.original_parent_id` — which, for a
  merged-away series whose folder became empty, was **deleted** during the same
  merge (`series_merge_service.py:314-323`);
- sets `file_row.status = FileStatus.inbox` but does **not** restore
  `book.series` (still points at the canonical series) and does not recreate the
  deleted `Series` row;
- so the net effect is a file misfiled into a dead/again-recreated folder, marked
  `inbox`, that the next organize/nightly run will just move back to canonical.

It's not data loss, but "Undo" on the Activity page silently doesn't undo.

**Fix:** either give series-merge Operation rows an action the undo path rejects
(a dedicated `series_merge` action, or reuse the "not undoable" guard), and offer
"re-run the merge the other way" instead; or make the merge apply idempotently
recreate the source series + folder on undo. Simplest safe option: exclude
merge-origin operations from `_UNDOABLE_ACTIONS` and say so in the UI. Prompt:
`prompts/10-series-merge-undo.md`.

### P2-4 — Unmetered AI spend paths

**Where:** `services/description_service.py:100-118` + `api/routes/library.py:120-131`;
`services/scan_service.py:221-281` (`run_rebuild`) + `api/routes/library.py:33-51`.

- `POST /api/library/descriptions?ai=true` runs `backfill_descriptions(use_ai=True,
  limit=None)`, which fans out one `anthropic_client.describe()` call per book
  still lacking a description — ROADMAP puts that at ~950 — with **no cap and no
  pre-flight cost estimate**. It's one checkbox + one button
  (`Library.tsx:280-295`); the only guard rail is a tooltip. Contrast the reident
  deep-check, which caps at 50 and shows a `$` figure first.
- `POST /api/library/rebuild` re-runs the full identification pipeline (AI
  included) for every file not already in `files`. After a "Clear Library" that's
  ~2200 identify calls, unattended once triggered, with no warning.

Neither is a runaway (both are bounded by real library size and are
user-initiated), but both are "click once, spend tens of dollars" with nothing
telling the user that in advance.

**Fix:** give the AI description backfill a per-run cap + an `estimate` endpoint
mirroring `reident_audit_service.estimate_deep_check`, and surface a
"~N books, ~$X" confirmation. Add a book-count + rough-cost note to the rebuild
confirmation. Prompt: `prompts/11-ai-spend-guardrails.md`.

  exactly matches another file … detected by content hash, not filename." —
  directly contradicts the `same_book` rows shown right below it (different bytes,

  three-tier confidence model that the code collapsed to two. `SPEC.md` §11 lists
  `confidence_auto_organize`/`_auto_flagged`/`_review_queue` but `config.py` only
  has the first two.
- **Viewer grants full `drive` scope to every family member who signs in**
  (`googleAuth.ts:41-43`, deliberate per ROADMAP). Re-affirming it's an accepted
  trade-off for a 2-person household; worth revisiting before the library is ever
  shared wider, since the scary consent screen + full read/write is a lot for a
  "browse the shelf" app.
- **`bookbrain-activity-log.json`** is plaintext in the shared Drive folder and
  records `who` (a self-reported first name) + search queries + downloads,
  readable by anyone with folder access. Fine at current scope; note it if
  sharing widens.
- **`book_repository._find_or_create_author` / `_find_or_create_series`**
  (`book_repository.py:88-96,105-119`) load every Author / every Series row and
  linear-scan with `normalize_words` on **every call** — O(n²) over a full
  `run_rebuild` of the ~2200-book library (~780 series). Fine for incremental
  scans; slow for rebuild.
- **`metadata_writeback_service._process_file`** has a narrow race: a `/correct`
  landing between `_write_one` (slow, unlocked) and the final commit stamps a now
  stale `embedded_metadata_key`, so the file is skipped on the next pass and
  keeps stale embedded metadata until the *next* correction. Self-heals, low
  impact.
- **Two `uvicorn app.main:app --port 8000` processes are currently running on
  this machine** (PID 48028 via `backend/.venv`, PID 42424 via system Python).
  Only one can hold `:8000`; the other is a straggler still holding the SQLite
  file open — the classic "database is locked" setup. Not a code issue; James
  should kill stale ones. (Checked before running the review's tests; the test
  suite uses an in-memory DB and was unaffected.)
