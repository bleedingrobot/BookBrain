## What's healthy

- **The identification pipeline is genuinely well-built.** `scan_service →
  candidate_service → identification_service → confidence_service →
  book_repository` is cleanly layered, the app-computed confidence is
  authoritative everywhere (no path routes on the model's self-report), and
  the whole `prompts/15` accuracy push (Stages 0 + A–K) landed with an
  offline eval harness gating every change (`pytest -m corpus`,
  `IDENTIFICATION-EVAL.md`). The invariant + mutation tests
  (`test_identification_invariants.py`, `test_identification_mutation.py`)
  encode "never confidently wrong" as executable guarantees.
- **Concurrency is taken seriously.** Every fuzzy find-or-create now serialises
  through one process-wide `book_repository.get_book_write_lock()` (the
  per-service locks were unified in `b9fc556`); Drive folder creation has its
  own per-path lock cache; `conftest.py` resets every module-level lock
  per-test for the pytest-asyncio per-loop-binding quirk.
- **Cost discipline.** Every model entrypoint is bounded and opt-in where it
  should be: `ai_verify_enabled` / `ai_web_search_enabled` default sensibly,
  `should_ground()` gates web search to ~3% of calls, descriptions + rebuild
  have caps and pre-flight `$` estimates, the reident "free pass" makes
  **zero** Anthropic calls.
- **Data-loss defence in depth.** sha256 + `original_sha256` sticky
  corrections, `same_book` duplicate detection excluded from bulk-clear, the
  viewer's 24h auto-rebuild safety net behind incremental sync, and now a
  nightly Drive backup of the DB with an automated restore (`prompts/18`).
- **Test suites all green:** backend **585 passed** (14 corpus/live
  deselected), `pytest -m corpus` **14 passed** (81.4% exact, 1 wrong
  auto-organize — unchanged, documented), frontend build + lint clean,
  library-viewer build + **90 tests** + lint clean. No failures, no flakes,
  no unexplained skips.

### P2

**F1 — Co-authored books collapse onto the primary author, non-deterministically.**
`book_repository._find_or_create_author` (backend/app/services/book_repository.py:110-133)
matches on `text_match.normalize_person_name`, which reduces
`"Dean Koontz, Kevin J. Anderson"` and `"George R. R. Martin; Gardner Dozois"`
to the same key as the solo author (`"dean koontz"`, `"george rr martin"`).
A new scan of a co-authored book therefore attaches it to the **solo**
`Author` row and files it in that author's folder, dropping the collaborator
from the library structure. The real DB has **23 author keys where a solo row
and a collaboration row currently coexist** (566 books under them — created
pre-Stage-J under the old word-set match); every future scan of one of those
collaborations now merges into the solo row. The eval corpus scores this as a
**miss** (`margaret-weis-tra`, `tony-diterlizzi-h`, `richard-awlinson`).
Whether a Koontz/Anderson book *should* live under `Dean Koontz/` or
`Dean Koontz & Kevin J. Anderson/` is a judgment call — but right now the
behaviour is undefined-by-accident and order-dependent.
*Fix:* decide the policy, then make `_find_or_create_author` deterministic. →
prompt 20. **DONE 2026-09-08 — James chose policy 1 (file under primary):**
`text_match.is_collaboration`, `book_repository._display_name` stores the
clean primary name, harness scores on the primary, `repair_forked_authors.py`
reworked. Author precision 94.8% → 96.6%.

**F2 — `repair_forked_authors.py` is a no-op on the real library.** *(done — prompt 20)*
It was guarded in `6768d3e` to skip any group mixing solo + collaboration
credits — which is now *every* group with a real fork, because the collab
credits share the primary-author key (F1). Genuine forks that should merge
(`Dean Koontz` / `Dean R. Koontz` — same person, 7 books; `Iain Banks` /
`Iain M. Banks`) can't be cleaned. The "most complete display name wins"
canonical pick is also wrong (it chose the *longest* string, i.e. a
collaboration credit). *Fix:* rework the grouping to (a) merge genuine
solo-name variants, (b) never touch solo+collab, (c) pick the shortest clean
solo name. → prompt 20 (folds into F1's session).

**F3 — a `library_rule` short-circuits at confidence 100 with an unverified title.**
`sticky_resolution.find_rule_match` (backend/app/services/sticky_resolution.py:95-108)
returns `computed_confidence=100`, `needs_human_review=False`, and
`title = evidence.title or filename` when an author/series alias matches. The
rule only carries an author/series alias — the *title* is still the raw EPUB
title (or the filename!), with no placeholder check and no confidence scoring.
A file with a junk title + a matching author-alias auto-organises at 100 with
that junk title. Only 1 `library_rule` exists today (a `series_alias`), so
this is rarely hit — but the design trusts a completely unvetted title.
*Fix:* run the resolved title through `metadata_sanity.looks_like_placeholder_title`;
on a hit, don't short-circuit (fall through to the normal path with the alias
still applied), or cap confidence and route to review. → prompt 21.

**F4 — `librarySync.ts` does a full tree rebuild on *any* sync error.** *(done — prompt 22)*
library-viewer/src/lib/librarySync.ts:157 — `catch {}` around the incremental
sync can't distinguish a stale Drive sync token (the one thing a rebuild
fixes) from a transient 500 / offline / rate-limit. Every blip triggers a
full `listLibraryTree` walk (hundreds of Drive calls on a 2,200-book
library) and hides real errors from `useLibrary`. *Fix:* rebuild only on the
stale-token signal (Drive returns 410 with `reason: "pageTokenExpired"`);
rethrow everything else so `runSync` surfaces it. → prompt 22.

**F5 — `cover_service` edge paths untested.** *(Overstated in the first draft —
see the correction.)* `_thumbnail` / `_phash_of_jpg` / `_make_one` and the
`regenerate_covers` happy + rehash + writeback paths *are* covered
(`test_cover_extract.py`, `test_cover_phash.py`). The real gaps: `nocover` /
`failed` counting through `regenerate_covers`, failure isolation across the
gather, `limit` bounding, and `_ensure_covers_folder` creating the folder.
*Fix:* 2 more cases in `test_cover_phash.py`. → prompt 23 (**done** —
downgraded to P3 in hindsight).

**F6 — `_find_or_create_author` / `_find_or_create_series` are O(rows) per file, under the global lock.**
Both do `select(Author)` / `select(Series)` — **every** row (446 authors,
590 series today) — materialise them and loop in Python, once per file, all
inside `book_repository.get_book_write_lock()` which serialises the entire
scan pipeline's DB phase. A post-`Clear Library` rebuild is
~2,200 × ~1,000 row-loads run strictly serially. Fine at today's size, but it
scales quadratically and it's on the hot path. *Fix:* a per-scan-batch
`{match_key: id}` cache, or a normalised, indexed match-key column. → prompt 24.

**F7 — restore artifacts and `backup-runs.log` aren't gitignored.**
`.gitignore` has `backend/*.db` and `backend/*.db.bak-*` and
`backend/nightly-runs.log*`, but **not** `backend/*.db.pre-restore-*` (left by
`app/jobs/restore.py`), `backend/*.db.before-restore` (the manual `RESTORE.md`
flow), or `backend/backup-runs.log*` (left by `app/jobs/backup_job.py`). A
`.pre-restore` file is a full DB copy including the (encrypted) OAuth token —
it must never land in git. *Fix:* three lines in `.gitignore`. → prompt 19
(trivial, do first).

### P3 (no prompt)

- **The module-level `asyncio.Lock` + hand-added `conftest` reset pattern is a landmine.** Six locks now (`book_repository`, `metadata_writeback`, `nightly`, `backup_job`, plus the two `FolderPathCache` maps); each needs a manually-added reset in `_reset_shared_singletons` or the next test to touch that singleton dies with "bound to a different event loop". An autouse fixture that resets a *registry* of locks would remove the footgun. All six are currently reset correctly.
- **The activity log stores raw search query strings** + a self-reported name in a plaintext Drive file readable by anyone with library-folder access. Low stakes for a 2-person household; worth James confirming he's OK with "who searched for what" being visible.
- **`_find_or_create_series` `SeriesAlias` lookup is exact `name.strip()`** (case/punctuation-sensitive). The word-set loop below is the real matcher, so this only misses a fast path; normalise it or drop it.
- **`backup_service._prune`** never cleans an orphaned `.sql.gz` (one whose `.db.gz` upload failed) — `_NAME_RE` only matches `.db.gz`. Cosmetic.
- **Rebuild cost estimate** (`estimate_rebuild`) uses a flat `ai_identify_cost_usd`; grounded calls (~3%, ~4× cost) make it ~10% low.
- **Doc rot:** `README.md` / `SPEC.md` / `ROADMAP.md` still title the project "EPUB Librarian"; `prompts/README.md`'s "Open" heading is stale (15–18 all shipped). `SPEC.md` §5 is superseded by §5a but not marked as such.
- **`ai_decisions` cache is effectively write-only for scan.** `scan_service` skips any file whose `drive_file_id` is already known (line 427), so `identify()` runs exactly once per file ever — the `sha256 + evidence_hash` cache key (SPEC §5 step 9) only matters for `reident_audit_service`. Not a bug; the SPEC wording overstates the cache's role.
- **No HTTP-level route tests** for `duplicates` / `operations` / `organize` / `settings` / `scan` / `wishlist` / `library_audit` / `local_scan`. The route layer is thin-wrapper-over-service and the services are well-tested, so this is low-value, but the request/response contract itself is unverified.
