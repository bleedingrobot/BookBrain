## 1. What's healthy

This is a lot of careful work and it mostly holds up under scrutiny.

- **The layering held through 7 new services.** `hardcover_reading_service`,
  `hardcover_recs_service`, `hardcover_lists_service`, `hardcover_prompts_service`,
  `hardcover_new_releases_service`, `hardcover_series_service`, `sff_news_service`
  all sit in `services/`, call Hardcover only through
  `providers/metadata/hardcover.hardcover_graphql`, and touch the DB only
  through a session. No `api/ → providers/` shortcut crept in.
- **Every Hardcover failure path returns `[]` / best-effort.** A dead feed, a
  rate limit, a malformed response — none of it fails a nightly run or a
  route; the viewer just shows less. `regenerate_*` in
  `library_index_service.py` all follow the "never raises into the caller"
  contract and it's honoured.
- **The confidence rule is intact.** `prompts/30–32` added zero Anthropic
  exposure — no new path reaches `AnthropicIdentificationClient`, and
  `ai_reported_confidence` still isn't threaded into routing
  (`identification_service.py`). SPEC §1's hard rule survives.
- **Test discipline stayed up.** 695 backend + 14 corpus + 190 library-viewer,
  all green; `frontend` build (typecheck) + lint clean. Every `prompts/31`
  part and `prompts/32` shipped with unit tests
  (`test_hardcover_{reading,lists,prompts}_service.py`,
  `test_sff_news_service.py`, `news.test.ts`, `readNextSnooze.test.ts`, …).
- **This session's two Hardcover bugs were fixed properly, not patched.** The
  per-minute-vs-daily rate-limit false positive (`8b71ac8`) and the
  `fetch_reading` silent truncation (`c9516e9`) were each traced to a root
  cause and fixed with a real mechanism (segment-parsed header check; a page
  retry loop + a `complete` flag + a partial-guard that won't shrink the
  sidecar). The `contributions(limit: 1)` → narrator-name bug in the same
  commit was fixed across all six query sites with a documented shared
  pattern.
- **Secrets are clean.** `backend/.env` is gitignored; no `hc_pat_` /
  unrestricted `AIzaSy` key ever appears in history
  (`git log --all -S`). The three baked defaults in
  `library-viewer/src/lib/config.ts` are genuinely public-safe (OAuth client
  id, a Drive folder id, a referrer-restricted Books-API key) and each is
  commented as such.
- **The sidecar pattern's rationale is sound.** The static viewer can't call
  Hardcover (CORS + secret token) or fetch RSS (CORS), so the backend writes
  JSON to the Drive folder and the viewer reads it with a modifiedTime-gated
  cache. That's the right shape; the issue below is that it's been
  copy-pasted eleven times.
- **No new lock landmine.** The 7 new services use per-call `_TokenBucket`
  instances (deliberately, to dodge the `conftest` per-loop lock rebind) —
  none added a module-level `asyncio.Lock`, so `conftest._reset_shared_singletons`
  is still the complete list.

## 2. System map (as of 2026-09-10)

### Backend (`api/ → services/ → providers/ → data/`, SQLite, async SQLAlchemy 2.0)

**Identification pipeline** (unchanged in shape since `prompts/15`):
`scan_service._process_file` → `identification_service.identify`
(library rules → sticky correction → deterministic evidence → providers
[Google Books, Open Library, Hardcover] → fast path [ISBN + ≥0.80 title sim]
→ AI [`AnthropicIdentificationClient`, forced schema, opt-in web-search /
verify] → `confidence_service.score` [authoritative] → threshold routing)
→ `book_repository.resolve_book` [shared `_book_write_lock`] →
`batch_prior_service` consensus lift → auto-organize → recently-organized tray.

**Hardcover integration** (`providers/metadata/hardcover.py` = `hardcover_graphql`
+ `_TokenBucket` + `HardcoverRateLimited` / `HardcoverUnavailable` +
`_is_daily_limit`):
- `hardcover_series_service` → `series.hardcover_json` (canonical book list)
- `hardcover_recs_service` → `books.hardcover_json` (`{id, similar[], meta{}}`
  — meta now carries rating / pages / category / genres / moods /
  contentWarnings / listsCount / published / audioHours)
- `hardcover_new_releases_service` → `authors.hardcover_json` + person-id
  resolution (`prompts/28`); `fetch_global_anticipated`, `fetch_trending`
- `hardcover_reading_service` → **reads** `me{user_books}` (status / rating /
  dates / `user_book_reads` progress) + `me{goals}`; **writes**
  `insert/update_user_book` (status) + `insert/update_user_book_read`
  (progress, advance-only) via `apply_pending`
- `hardcover_lists_service` → featured lists containing owned books →
  candidates
- `hardcover_prompts_service` → top community prompts → owned answers

**Sidecars** (`library_index_service.regenerate_*`, all → the Drive library
folder, all best-effort):
`bookbrain-index.json` (v7) · `-recommendations.json` · `-new-releases.json`
(v2) · `-reading.json` (v4) · `-reading-pending.json` (viewer-written queue) ·
`-news.json` · `-news-dismissed.json` (viewer-written) ·
`-readnext-snoozed.json` (viewer-written) · `-prompts.json` · `-lists.json` ·
`-wishlist.json` (viewer-written) · `-activity-log.json` (viewer-written) ·
`-viewer-settings.json` (viewer-written) · `-embeddings.bin` ·
`bookbrain-sent-*` (per-device).

**Jobs**: `nightly.run_nightly` — ~13 steps
(pull-local → backup → scan[+organize] → covers → hc-series → hc-recs →
hc-new-releases → reading → prompts → lists → news → index → embeddings),
each token-/folder-gated and never-fails-the-run; APScheduler in-process +
`python -m app.jobs.nightly`. `backup_job` on its own schedule.

**Shared matcher**: `library_index_service.match_hardcover_book_ids(session, ids)`
— Hardcover book id → owned drive id off `Book.hardcover_json.id` (exact),
used by lists (E2) + prompts (F).

### library-viewer (static React, GitHub Pages, auto-deploy on push)

`App.tsx` orchestrates; a `requestIdleCallback`-deferred effect fires **9
sidecar fetches** on load (newReleases, reading, reading-pending, news +
news-dismissed + prune, prompts, lists, readnext-snoozed) — each a Drive
`files?q=` list call plus an `alt=media` download when present (~18 Drive
calls/load), on top of the eager `index` + `viewer-settings` and the
first-interaction `recommendations` / `embeddings.bin`.
`librarySync.ts` = incremental Drive changes-feed + a 24h full-walk safety
net. `Reader.tsx` = vendored foliate-js + IndexedDB offline cache.

### frontend (local admin, Vite, TanStack Query)

Pages: Dashboard / Inbox / ReviewQueue / Library / Duplicates / Activity /
LibraryAudit / Wishlist / Settings. `api.ts` exposes scan / organize / review
/ duplicates / audit / backup / **index + covers + descriptions +
embedded-metadata** — but **not** any Hardcover or discovery-sidecar refresh
(see F5).

## 3. Findings

### P1

#### F1 — `apply_pending` can mark the WRONG book as read on Hardcover — **DONE 2026-09-10 (prompts/33)**

`_resolve_book_id`'s fuzzy fallback now runs `_confident_match` (title equal
after `normalize_title`, or after stripping a leading "Series: " prefix, or
`title_similarity >= 0.9`, **and** an author from the hit
`normalize_person_name`-matches) before accepting a hit; no match → `None` +
an INFO log. Separately, per James's call, the reader no longer auto-marks a
book read on finish at all (viewer `App.tsx` — deliberate ✓ button only).

`app/services/hardcover_reading_service.py:189-203` (`_resolve_book_id`).

When a queued reading change has no ISBN (or the ISBN doesn't resolve on
Hardcover), `_resolve_book_id` falls back to
`search(query: "<title> <author>")` and returns
`hits[0]["document"]["id"]` **with no title or author similarity check**.
`apply_pending` then calls `_apply_status` / `_apply_progress`, which
**mutate that book's `user_book` on James's real Hardcover account**.

The ISBN-less path is the *common* case, not the edge — the reading sidecar
shows nearly every owned book (all of the Dresden Files, etc.) with
`isbn=None` in the library index, because most `Book` rows have no ISBN
identifier. So most "mark read" write-backs go through the unchecked search.

Contrast the identification pipeline, which requires `title_similarity >= 0.80`
even on an *ISBN* match (SPEC §5a "a wrong-but-valid ISBN falls through to
AI"). The write-back has zero equivalent guard, and it's writing to an
external account rather than a local DB.

Concrete failure: the reader auto-marks a book read on close at ≥ 98 %
(`App.tsx` `onClose` → `markReadingStatus(row, 'read')`). Finish an owned
"Death Masks" epub that has no ISBN → `_resolve_book_id` searches
`"Death Masks Jim Butcher"` → if the top Hardcover hit is a box set, an
audiobook bundle, or a foreign edition, *that* gets `status_id: 3` +
today's `last_read_date` written to James's shelf. Silent — nothing in the
viewer or the nightly summary says which Hardcover book was touched.

**Fix**: after the search, accept the hit only when
`normalize_title(hit.title)` matches `normalize_title(change.title)` (allowing
a leading `"<Series>: "` prefix on the Hardcover side) **and** an author from
the hit `normalize_person_name`-matches `change.author`. On no confident
match, return `None`; `apply_pending` already routes that to `failed` (the
change stays queued). Log the rejected candidate so it's diagnosable.
Covered by `prompts/33`.

### P2

#### F2 — a permanently-unresolvable write-back is retried every night, forever — **DONE 2026-09-10 (prompts/33)**

`_prune_pending_changes` carries an `attempts` count on each failed change and
drops it after 5 (`_MAX_WRITEBACK_ATTEMPTS`), with a WARNING. A change not
attempted (rate-limited mid-queue) is kept untouched.

`app/services/library_index_service.py:915-926` (`regenerate_reading`).

`left = [c for c in pending if c["driveFileId"] not in done]` keeps every
`failed` change in the pending file. If James marks read a book that simply
isn't on Hardcover (or fails F1's new match check), that change is retried on
every sync — 2 Hardcover calls each time (`_BOOK_BY_ISBN` + `_BOOK_SEARCH`) —
and `bookbrain-reading-pending.json` never drains.

**Fix**: stamp `attempts` (or a `firstQueuedAt`) on each change; drop it from
`left` after ~5 consecutive failures or ~30 days, logging what was dropped.
Covered by `prompts/33`.

#### F3 — viewer→Drive sidecar writes have no concurrency control; `reading-pending` can silently lose a "mark read"

`library-viewer/src/lib/drive.ts:writeJsonFile` + every caller
(`readingQueue.ts`, `news.ts`, `readNextSnooze.ts`, `wishlist.ts`,
`activityLog.ts`, `koboDeviceSync.ts`).

`writeJsonFile` is an unconditional full-file `PATCH …?uploadType=media`.
The read-modify-write callers (`queueReadingChange`, `dismissNewsItem`,
`snoozeReadNext`, `addToWishlist`) read the file, merge, and write back with
**no lock and no `If-Match`**. Two devices (or two tabs) acting inside the
read→write window → last write wins on the *whole file*.

For the wishlist / activity-log this is a known-accepted trade
(`activityLog.ts` says so). But **`bookbrain-reading-pending.json` is a sync
*queue***: a clobbered entry is a "mark read" that never reaches Hardcover and
that James has no way to notice — it's silent data loss, not a lost log line.
This session added two more RMW sidecars (`news-dismissed`, `readnext-snoozed`)
in the same shape; `dismissNewsItem` / `snoozeReadNext` serialise their *own*
writes via a module promise-chain, but that doesn't help a second *device*.

**Fix**: thread the Drive `etag` through `readJsonFile`'s return, send
`If-Match: <etag>` on the `PATCH`, and on `412 Precondition Failed` re-read →
re-merge → retry (bounded). This closes the whole class for every RMW sidecar
at once, so do it inside the shared helper from F6. Covered by `prompts/34`.

#### F4 — a persistently-partial reading pull freezes the sidecar with no signal — **DONE 2026-09-10 (prompts/33)**

A `reading_partial_streak` setting counts consecutive partial-and-smaller
pulls; after 3 the partial payload is written anyway with `partial: true` +
a WARNING, and the viewer shows a one-line amber note under the Read/Unread
chips. Any successful write resets the streak.

`app/services/library_index_service.py:950-965` (added this session,
`c9516e9`).

The guard is correct — it refuses to overwrite a good `bookbrain-reading.json`
with a *smaller* partial pull (which would make read books look unread). But
if Hardcover is flaky *every* night (one page fails each run), the sidecar
never updates, and the only trace is `reading: skipped` in the nightly
summary — indistinguishable from "no token". James sees stale read/unread
state indefinitely.

**Fix**: track consecutive partial runs; after ~3, either write the partial
with a `partial: true` flag the viewer surfaces ("reading data may be
incomplete"), or escalate it in the nightly summary / a dashboard warning.
Covered by `prompts/33`.

#### F5 — the admin app can't refresh any Hardcover / discovery sidecar — **DONE 2026-09-10 (prompts/35)**

`frontend/src/services/api.ts:207-236`.

`api.ts` has `refreshLibraryIndex`, `generateCovers`, `backfillDescriptions`,
`writeEmbeddedMetadata` — but nothing for `book-recs/refresh`,
`series-catalog/refresh`, `new-releases/refresh`, `/new-releases`, `/reading`,
`/prompts`, `/lists`, `/news`, or `/embeddings`. Those routes exist and this
session needed them re-run by hand (via `curl`) repeatedly — after the
rate-limit truncation, after the narrator-name fix, after the feed retune.
The nightly covers steady state, but when a sidecar is *wrong* James — who is
"not terminal-savvy" — has no recourse but to wait for a nightly that may hit
the same bug.

**Fix**: a "Discovery data" card in Settings: one row per sidecar with a
"Refresh" button (POST the route) and a last-generated / age readout (from the
sidecar's `generatedAt`, fetched via the existing Drive-read path or a small
`GET /api/library/discovery-status` endpoint). Covered by `prompts/35`.

#### F6 — sidecar sprawl: 11 hand-rolled fetch modules, 3 now also hand-rolling cache+sync+serialised-write

`library-viewer/src/lib/`: `libraryIndex.ts`, `recommendations.ts`,
`newReleases.ts`, `reading.ts`, `news.ts`, `prompts.ts`, `lists.ts`,
`readNextSnooze.ts`, `wishlist.ts`, `activityLog.ts`, `readingQueue.ts`.

Every one of these re-implements the same ~40-line dance: build a Drive
`files?q=name=…` query, list, compare `modifiedTime` to a `localStorage`
cache key, `alt=media` download, `try/catch` to the cached value.
`news.ts` and `readNextSnooze.ts` additionally each duplicate `cachedX()` /
`XSynced()` (read-merge-seed) / a module-level `writeChain` / a `pruneX()`.

This is the "N near-identical files is telling you the design wants a
primitive" case. It's not a bug today, but it's where the *next* bug will be
seeded (a cache key typo, a missing `try/catch`, an inconsistent
merge), and F3's fix has to land in all of them.

**Fix**: one `syncedSidecar<T>(filename, { cacheKey, parse, empty, merge? })`
returning `{ cachedNow(): T, synced(token, folder): Promise<T>,
write(token, folder, next): Promise<T> }`, with the F3 ETag-retry built in.
Migrate the read-only sidecars first (mechanical), then the RMW ones.
~400–500 lines net removed, no behaviour change. Covered by `prompts/34`.

#### F7 — reading-match is title+author-key only, and a missed match is silent — **DONE 2026-09-10 (prompts/33)**

`build_reading_payload` now logs (INFO, bounded to 20/run) an unmatched
*read* Hardcover row whose normalised title — raw or with a leading
"Series: " stripped — is a substring of an owned title, naming both.

`app/services/library_index_service.py:build_reading_payload` (~823-853).

Just fixed the narrator-name bug (`c9516e9`); the residual gaps:
- `key_to_drive = {_norm_key(t, a): d for …}` — a `_norm_key` collision
  (two owned books normalising to the same `title|author`) silently keeps
  whichever the dict comprehension saw last.
- `books.setdefault(drive, entry)` — if two Hardcover rows map to one drive
  id, the second is silently dropped.
- Near-miss titles (`"The Dresden Files: Storm Front"` from a graphic-novel
  edition vs `"Storm Front"`) don't match and there's **no log line** — a
  read Hardcover book that clearly corresponds to an owned library book just
  vanishes into the `unmatched` count.

No test asserts collision behaviour.

**Fix**: when a *read* Hardcover row fails both ISBN and key match, and its
`_norm_key` title (after stripping a leading `"<word(s)>: "` prefix) is a
substring of an owned title (or vice versa), log it at INFO with both sides —
so the next "why is X unread" is one `grep` away. Optionally add a fuzzy
fallback mirroring the identification pipeline's `title_similarity`.
Covered by `prompts/33`.

#### F8 — `feedparser.parse` runs with no timeout — **DONE 2026-09-10 (prompts/36)**

`app/services/sff_news_service.py` `_fetch_one` →
`asyncio.to_thread(_parse_feed, resp.content, name)`.

The HTTP GET is bounded (`_TIMEOUT = 12.0`), the *parse* is not. `feedparser`
on a pathological feed (enormous, deeply nested XML, billion-laughs-ish) can
run for a very long time, and 11 feeds are dispatched concurrently — a
wedged parse holds a thread-pool thread and the nightly news step never
returns. These are trusted feeds, so likelihood is low, but a hijacked feed
or a CDN serving garbage is the failure mode, and the news step has no
overall deadline.

**Fix**: `await asyncio.wait_for(asyncio.to_thread(_parse_feed, …), timeout=15)`;
on `TimeoutError` skip that feed (best-effort, same as a 404). Covered by
`prompts/36`.

**Order:**

1. **`33` first** — it's the only P1, it's the gap in the reading write-back's
   own justification, and the reader auto-marks books read without James
   lifting a finger, so a wrong match ships to his account silently. Small,
   self-contained, backend-only.
2. **`36`** — five-minute change, removes a (low-probability but total)
   nightly-wedge risk. Do it while you're in the backend.
3. **`34`** — the biggest, but pure structure + one real fix (F3). Landing it
   makes every future sidecar cheaper and safer. No user-visible change, so
   low risk to ship. `33`'s reading-pending changes will be easier to reason
   about on top of it, but `33` shouldn't wait for `34`.
4. **`35`** — quality-of-life; do it last. It's the safety valve for "a
   sidecar went wrong" — worth having, not urgent, and the other three reduce
   how often it's needed.

`33` and `36` are independent and could go in one session. `34` and `35` are
independent of each other and of `33`/`36`.
